ADR-017: Opt-In Prerequisite Provisioning

Status: Accepted Date: 2026-10-17

Context

ADR-016 promised one command that produces a working install. In practice the first thing a new machine fails on is the thing Scopra cannot supply itself: rootless Podman. The preflight refuses to continue without it, correctly, and then prints "install Podman 4.0 or later" — which is exactly the manual step the one-command install was supposed to remove. The user is left reading a fix line and typing it into another terminal.

The distribution already knows how to install Podman. Every supported family has a package manager, a package named podman, and repositories the user already trusts for their system updates. What the installer lacks is not knowledge but permission.

Two rules from the existing design pull in opposite directions here:

  • the install must be fail-closed and must not silently change the machine;
  • the install must be one command, and stopping at the first missing package is a failure of that promise.

Decision

The installer may offer to install a missing prerequisite with the distribution's own package manager, and only after the user asks for it and confirms the exact commands.

The rules, in order of importance:

  1. Nothing runs by default. The preflight screen gains one line — Press f and the installer can install it for you — and one footer key. The confirmation screen prints every argument vector that will run. y runs them; Enter, n, and Escape cancel. --yes never provisions.
  2. The plan is derived, not guessed. /etc/os-release is read for ID and ID_LIKE; a family is chosen from a fixed table; the package manager must be present; and sudo must be present when the process is not root. An unknown distribution or a missing tool produces no plan at all, and the screen falls back to the manual instructions. There is no "try apt, then dnf" fallback.
  3. Commands are argument vectors. The installer never builds a shell string and never runs a shell: sudo, dnf, install, -y, podman is executed as argv. Nothing read from os-release or a terminal can become syntax.
  4. The terminal is handed over, not shared. Before the child runs, the interface retires its key reader, leaves the alternate screen, and restores the original terminal settings. sudo prompts for a password the way it always does, in the clear, with echo on. The installer never reads, stores, or forwards the password, and it takes the terminal back afterwards.
  5. The install itself still never escalates. install.sh runs no privileged command, and scopra install writes only into the install directory and the user unit. Provisioning happens before that, as a separate, deliberate act.
  6. Failure is reported, not hidden. The command's output stays on the screen (the alternate screen is gone while it runs), and a non-zero exit returns the interface to the preflight with the failure line and the manual commands. A package that is too old for Scopra — Ubuntu 22.04 ships Podman 3.4 — shows up as the same failed check, with the version, after the attempt.

The plan today covers Debian/Ubuntu (apt-get with uidmap, slirp4netns, and fuse-overlayfs, which rootless Podman needs there), Fedora/RHEL and derivatives (dnf), Arch (pacman), openSUSE (zypper), and Alpine (apk).

Amendment: delegation is tested in the service context (2026-10-18)

Installing Podman was not enough. The first reported failure was cgroup controllers not delegated: cpu after package provisioning. The initial explanation blamed a user-manager restart and told the user to log out and back in. That advice was not supported by the diagnostics: the user manager had cpu available, while the desktop terminal's app.slice cgroup exposed only memory and pids.

Podman reports controllers for the cgroup of the podman process. A terminal probe therefore does not prove what the daemon's systemd unit can use. The installer and scopra doctor now run the read-only probe through an exact argument vector equivalent to:

systemd-run --user --quiet --pipe --wait --collect \
  --property=Delegate=cpu cpuset io memory pids -- \
  /absolute/path/to/podman info --format json

The generated scoprad.service requests the same Delegate=cpu cpuset io memory pids. Hollow's runtime preflight is unchanged: it still checks the actual daemon process context and refuses every run when required controllers are missing. The installer never treats a successful terminal-scope probe as a substitute for that check.

The opt-in user-manager drop-in remains available when controller absence is identified and the file is not already configured:

[Service]
Delegate=cpu cpuset io memory pids

at /etc/systemd/system/user@.service.d/99-scopra-delegate.conf, followed by systemctl daemon-reload. The rules remain:

  1. No shell redirection, even for a file. The drop-in is written to the user's state directory first, then installed by mkdir, cp, and chmod argument vectors. The screen prints those commands, so the file the user approves is the file that lands.
  2. Only when it can work. The offer requires Podman 4.0+, rootless, cgroups v2, and the required systemd tools. On cgroups v1 the fix would be a boot parameter and a reboot, which this installer does not touch. If the delegated probe itself fails, a direct Podman query may classify a missing controller for provisioning; that query can never make preflight pass.
  3. Verify the effect, not a presumed login boundary. After an explicitly approved plan completes, the installer re-runs the delegated service probe in the same session. If it still fails, the failed check is shown and the install remains blocked. The installer does not restart user@.service, claim that logging out will fix it, or offer the same already-installed drop-in again.
  4. A no-service install tests its real launch context. If scoprad is present and the user opts out of the systemd unit, the installer additionally runs podman info in the current process cgroup, where the user will start the daemon manually. A failure blocks the install before binaries are written; a passing transient-service probe alone is not enough.

The earlier same-session loop and relogin screen were symptoms of using the wrong cgroup as evidence. The check now follows the process context that will execute Hollow instead of guessing at systemd lifecycle behavior.

Consequences

  • The one command can install Podman and, when explicitly approved, delegate cgroup controllers. A systemd-managed install is accepted only after the transient service probe passes; an explicit no-service install must also pass in the current process context where the daemon will be started.
  • The installer can change the system in a way it could not before. That is a real trust expansion, bounded by: it is opt-in, it is visible before it runs, it runs only the distribution's package manager against the distribution's repositories, and it requires an explicit y that cannot be a stray Enter.
  • sudo is now something the installer can invoke. The documentation, install.sh's header, the welcome screen, and ADR-016 all had to stop saying "the installer never runs sudo" and start saying "the install never runs sudo; a missing prerequisite is offered with the exact command".
  • Provisioning is Linux-only, like everything else. macOS still exits before it downloads anything.
  • A distribution with a Podman older than 4.0 is not fixed by this: the plan installs what the repositories have, and the check then honestly reports the version. Solving that needs a second source (backports, a newer release, or a static build) and a trust decision this ADR does not make.
  • The sandbox image is still the user's choice. The installer does not pull images: a digest is a security decision, and Mio's rule is that what runs is exactly what is already in local storage.

Alternatives considered

  • Keep printing instructions only. Rejected: it is the status quo that this ADR exists to fix, and it fails exactly the user who is new to Podman.
  • Install without asking. Rejected without much debate: silent privilege escalation from a curl | sh one-liner is the pattern the project exists to avoid.
  • Ask for the password inside the interface. Rejected: it would mean owning a credential prompt, and a bug there leaks a password. Letting sudo do its own job on a real terminal is both smaller and more familiar.
  • Download a static Podman or a release binary. Rejected: an unverified binary from a non-distribution source, outside the user's update path, is a worse trust story than the distribution's own package.
  • Auto-detect the package manager by trying each one. Rejected: a failed dnf on Debian is noise, and "try until something works" is not a security posture.
  • Provision the sandbox image too. Deferred, not rejected: pulling an image needs a digest the user chose, and this installer does not get to choose what the sandbox runs.
